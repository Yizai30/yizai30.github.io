## 预备知识

- **RPC**：Remote Procedure Call，远程过程调用，一端发起“调用某方法并传参”的请求，另一端（或服务器）在本地执行该方法。
- **Peer**：网络中的一个参与方（服务器/客户端/进程），每个 peer 有一个唯一的 ID。
- **Authority**：决定哪个 peer 被允许修改某个网络对象状态。
- **Channel**：在同一个连接里划分多个逻辑通道，每个通道可以有自己可靠/有序语义。
- **Reliable**：保证消息最终到达并按顺序交付（通常通过重传与确认实现），与之对应的有 Unreliable，只管发不管对方是否收到。
- **Replication**：把某个对象的存在（spawn/despawn）与状态在多个 peers 间保持一致的过程。
- **ENet**：基于 UDP 的可靠实时网络库，提供可靠/不可靠通道、分片与重传等功能。

> Godot 提供的高级网络功能，即封装好的 RPC 和 Replication 的便捷接口。同时 Godot 还有另一套方案，即提供了可选的“低级网络”，可以直接操作更底层的网络接口，控制精度更高。

## 1 Peer

Peer 是网络中的一个参与方，拥有唯一的 UID。

### 1.1 代码示例

Godot游戏大厅示例：[https://docs.godotengine.org/zh-cn/4.x/tutorials/networking/high_level_multiplayer.html#example-lobby-implementation](https://docs.godotengine.org/zh-cn/4.x/tutorials/networking/high_level_multiplayer.html#example-lobby-implementation)

```python
extends Node

...

func join_game(address = ""):
	if address.is_empty():
		address = DEFAULT_SERVER_IP
	var peer = ENetMultiplayerPeer.new()
	var error = peer.create_client(address, PORT)
	if error:
		return error
	multiplayer.multiplayer_peer = peer


func create_game():
	var peer = ENetMultiplayerPeer.new()
	var error = peer.create_server(PORT, MAX_CONNECTIONS)
	if error:
		return error
	multiplayer.multiplayer_peer = peer

	players[1] = player_info
	player_connected.emit(1, player_info)


func remove_multiplayer_peer():
	multiplayer.multiplayer_peer = OfflineMultiplayerPeer.new()
	players.clear()
```

**标识每个 Peer**：在 Godot 中，只要有一个进程接入了网络，它就是一个 peer，每个 peer 都会有一个在整个网络中唯一的 UID（用户标识符），服务器 Peer 的 UID 固定是 1，客户端 Peer 的 UID 是服务器随机分配的一个正整数。

**管理场景中 Peer 的创建和销毁**：使用高级网络功能时，主要关注当前场景中 peer 的创建和销毁。上面是扩展 Node 并操作 peer 对象状态的几个函数，实现是通过给 Node 节点的 multiplayer 字段的 multiplayer_peer 属性赋值，让它使用 ENet 的这种实现。一个场景下的 Node 节点，绝大多数都共享同一个 multiplayer 实例。当要停用网络功能时，我们只需要给 multiplayer 字段赋一个 OfflineMultiplayerPeer 对象即可。

**Godot 中 Peer 扮演的角色**：另外，在 Godot 中，Peer 并不只是扮演传统的客户端/服务器来组成C/S架构，还可以通过调用 ENetMultiplayerPeer 的 create_mesh 方法，切换到 Mesh 网络模式，让每台客户端直接与其他客户端相连，形成一个去中心化的点对点（P2P）网络。

### 1.2 具体实现思路

**实现细节：**

- **在 Node 上访问的 multiplayer 字段**，实际上是位于 SceneTree 上的 MultiplayerAPI 类型的字段，在 Godot 的默认行为中会被初始化为 SceneMultiplayer 类型的实例，peer 是 multiplayer 字段的 multiplayer_peer 属性，被封装在了 SceneMultiplayer 类型中
- **RPC**，需要 MultiplayerAPI 实例提供的 rpcp 函数
- **MultiplayerSpawner（管理对象生成） & MultiplayerSynchronizer（实现对象同步）**，需要 MultiplayerAPI 类的实例提供的 object_configuration_add 和 object_configuration_remove 接口

在 Godot 的 **高级网络设计** 里，相对“低级网络”可以使用便捷的接口，Peer 是如何扮演不同的角色的呢？
- 网络中的角色，服务器、客户端，或者 P2P 节点，都是 Godot **高级网络** 部分的概念，这些角色的本质区别在于，**建立网络连接和处理网络事件的方式** 不同。

Godot 的高级网络向我们屏蔽了底层的网络事件处理细节，如果我们想自己处理这些细节，如何通过 Godot 的低级网络封装来实现呢？（没有MultiplayerAPI）
- **ENetAddress**：IP + port 的地址结构（用于 enet_host_create 绑定或 enet_host_connect 指定目标）。
- **ENetHost**：代表一个 ENet 主机（server 或 client socket 的封装），管理监听、peer 列表、通道数等。
- **ENetPeer**：代表与单个远端主机的会话（peer），包含状态、队列、序号、RTT 等信息
- **ENetPacket**：单个发送/接收的数据包对象（包含数据与释放策略）
- **ENetEvent**：enet_host_service() 返回的事件（CONNECT / RECEIVE / DISCONNECT / NONE），携带 ENetPeer* / ENetPacket* 等
- **ENetChannel** / **ENetProtocol** / **ENetCallbacks** / **ENetCompressor**：协议/通道级别的内部或可选扩展接口（回调、压缩器、协议细节）
- Godot 暴露给我们使用的是 **ENetConnection** 和 **ENetPacketPeer** 两个类，它们的作用分别是：
  - **ENetConnection**：对 ENetHost 的直接封装。负责创建/绑定主机、发起连接，轮询 enet_host_service 返回的事件，以及分配和管理 ENetPacketPeer 等。和 ENetHost 差不多，需要自己实例化一个 ENetConnection 来进行操作。
  - **ENetPacketPeer**：对单个远端对话 ENetPeer 以及相关入站数据包 ENetPacket 的封装，它内部维护着一个 ENetPacket 指针队列，当 ENetConnection 执行 service() 方法轮询事件并收到 RECEIVE 消息时，就会把数据包放入相应 ENetPacketPeer 的队列中。用户再通过 ENetPacketPeer 的 get_packet() 方法取出来。ENetPacketPeer 无法直接实例化，它在 Godot 中唯一出现的地方，是在调用 ENetConnection 的 service() 方法进行事件轮询后，所返回的数组（Array）中的第二个元素（即下标为 1 的那个）

## 2 Authority

Authority 是一种决定哪个 Peer 有权修改某个网络对象状态的权力分配机制。

在 Godot 4.5 引擎源码的 scene/main/node.h 的大约第 50 行的位置，可以看到比较长的 Node 类的声明，其中关于 Authority 的关键部分如下：

```cpp
class Node : public Object {
	GDCLASS(Node, Object);

private:

	struct Data {
		// ...
		int multiplayer_authority = 1; // Server by default.
	} data;

	Ref<MultiplayerAPI> multiplayer;
}
```

multiplayer_authority 默认是 1，它存储的是拥有该节点权威的 Peer 的 UID，默认表示该节点由服务器拥有权威，也就是那个调用了 create_server 方法的 Peer 端。在这样的设计下，既可以实现 C/S 架构，也可以实现 P2P 架构：
- **C/S 架构中**，通常只有服务器拥有绝大多数节点的权威，客户端就像连接到服务器上的键盘鼠标，只向服务器发送操作的输入，服务器接收并校验后，再将节点的最新状态同步下发到各个客户端，这是现代大多数有专业服务器支持的网络游戏采用的思路。
- **P2P 架构中**，每个客户端都拥有自己操控节点的权威，并负责将自己节点的数据同步给网络中的其他玩家，这种去中心化的思想，在没有条件设立专业服务器的小型游戏中更常见，也曾是上个世纪游戏主流的联机方案。

## 3 RPC

RPC 是一种可以在其它 Peer 上调用的函数。

> RPC 本质上只区分“本地”和“远端”，而“客户端”/“服务器”、“权威端”/“非权威端”，是我们根据游戏业务逻辑自己赋予的“角色”。

Godot 通过 @rpc 注解标记 RPC 函数。该注解有 4 个参数：
1. **权力分配模式 mode**："authority" / "any_peer"（规定谁有权力发起这个调用："authority" 表示仅权威端，在经典的 C/S 架构里，权威端就是服务器，所以需要服务器计算出最终状态，然后通过 RPC 广播给所有客户端；"any_peer" 表示网络中的任何参与方，客户端和服务器都可以发起这个调用，所以适用于玩家移动、开枪这种由客户端主动发起的操作指令）
2. **同步模式 sync**："call_remote" / "call_local"（决定 RPC 被调用时，去哪里执行它的逻辑："call_local" 表示本地节点也会执行一遍，该模式适用于需要在本地立刻看到效果，同时也需要通知远端的场景；"call_remote" 表示本地节点不会执行，仅远程节点执行，该模式适用于客户端向服务器发送请求，或服务器向客户端下发命令的场景）
3. **传输语义 transfer_mode**："unreliable" / "unreliable_ordered" / "reliable"（"unreliable" 表示不确认数据包是否到达接收方，并且到达顺序不确定，也就是说接收端执行函数的顺序也不一定和发送顺序一致；"unreliable_ordered" 表示数据包不一定能够到达接收方，但是通过阻塞等待/超时丢弃保证到达顺序；"reliable" 表示通过阻塞等待⌈数据包到达了也会被阻塞以确保顺序⌋/超时重传⌈若一段时间没有收到返回的“确认”，便认为包丢了，重新传输⌋，数据包一定能够到达接收方，并且保证了数据包的到达顺序，但具有明显的性能损失⌈所谓的“队头阻塞”问题⌋）
4. **信道索引 transfer_channel**：一个整型，默认通道是 0，此时实际上作为 3 个独立的通道工作（作用是把不同类型的数据流隔离开，就像马路上划分车道，例如可以把实时更新的玩家位置、语音聊天这些可以容忍丢失的数据放在一个不可靠信道上，而把释放技能、购买物品这种关键指令放在一个可靠信道上，这样它们就不会互相干扰了）

### 3.1 代码示例

Godot 文档，远程过程调用：[https://docs.godotengine.org/zh-cn/4.x/tutorials/networking/high_level_multiplayer.html#remote-procedure-calls](https://docs.godotengine.org/zh-cn/4.x/tutorials/networking/high_level_multiplayer.html#remote-procedure-calls)

### 3.2 传输语义和信道索引的底层实现

传输语义 transfer_mode 和信道索引 transfer_channel 的底层逻辑其实是分别考虑的，两者配合实现了信道选择和传输方式。

我们可以通过查看引擎源码来分析：

在 modules/enet/enet_multiplayer_peer.h:49-53
```cpp
enum {
	SYSCH_RELIABLE = 0,      // 可靠传输的保留通道
	SYSCH_UNRELIABLE = 1,    // 不可靠传输的保留通道
	SYSCH_MAX = 2            // 保留通道数量
};
```
在对信道索引的定义中，SYSCH_RELIABLE、SYSCH_UNRELIABLE 分别为在自动选择传输信道时的系统的保留通道 0、1；SYSCH_MAX 为在用户自定义传输信道时的信道索引边界，它使得用户自定义的信道索引 ≥ 2，而不会和保留的信道索引冲突。

在 modules/enet/enet_multiplayer_peer.cpp:341-359
```cpp
int channel = SYSCH_RELIABLE;  // 初始化为 0
int tr_channel = get_transfer_channel();  // 赋值为用户自定义的通道

// 首先根据 transfer_mode 选择默认的传输模式（通过 packet_flags 实现），并自动选择保留通道（通过 channel 实现）
switch (get_transfer_mode()) {
	case TRANSFER_MODE_UNRELIABLE: {
		packet_flags = ENET_PACKET_FLAG_UNSEQUENCED |
ENET_PACKET_FLAG_UNRELIABLE_FRAGMENT;
		channel = SYSCH_UNRELIABLE;  // channel = 1
	} break;
	case TRANSFER_MODE_UNRELIABLE_ORDERED: {
		packet_flags = ENET_PACKET_FLAG_UNRELIABLE_FRAGMENT;
		channel = SYSCH_UNRELIABLE;  // channel = 1
	} break;
	case TRANSFER_MODE_RELIABLE: {
		packet_flags = ENET_PACKET_FLAG_RELIABLE;
		channel = SYSCH_RELIABLE;  // channel = 0
	} break;
}

// 关键判断：tr_channel > 0 时覆盖上面选择的信道
if (tr_channel > 0) {  // 若用户设置信道为 1 > 0，条件为真！
	channel = SYSCH_MAX + tr_channel - 1;  // 那么，channel = 2 + 1 - 1 = 2，即选择系统保留的 0、1 两个信道的下一个信道
}
```

可以看出，**传输语义 transfer_mode**，是通过 packet_flags 的变量值决定的：
- "unreliable" 对应 ENET_PACKET_FLAG_UNSEQUENCED |
ENET_PACKET_FLAG_UNRELIABLE_FRAGMENT
- "unreliable_ordered" 对应 ENET_PACKET_FLAG_UNRELIABLE_FRAGMENT
- "reliable"，对应 ENET_PACKET_FLAG_RELIABLE

而 **信道索引 transfer_channel**，是通过 channel 的变量值决定的：
- 在被赋值为默认值 0 时，总会根据传输语义自动选择默认的保留通道（0 或 1）。
- 而在其被赋值为 >0 的值时，会根据 SYSCH_MAX 选择保留通道之外的通道。

所以，我们在指定信道索引为推荐的 0 时，Godot 会自动根据 transfer_mode 分配可靠/不可靠的信道，而我们在指定信道索引为 >0 的整数时，需要管理好适用于可靠/不可靠通道的数据分别使用的信道索引，因为此时不再有自动选择通道的逻辑，我们要手动确保通道索引不冲突，使每个通道专注于一种传输模式。

## Replication

Replication 是负责一整套完整的网络对象的生命周期管理的机制。

管理一个网络对象：
- **何时创建**：权威端创建对象，并可靠地通知其它端让它们本地实例化同样的对象。
- **何时同步值**：按脏标记/差分发送更新。
- **何时销毁**：权威端移除对象，并可靠地通知其它端相应地删除对象。

在 Godot 引擎里，这些功能主要由 MultiplayerSpawner 和 MultiplayerSychronizer 两个节点来分工合作：
- **MultiplayerSpawner**：负责“谁存在”、“什么时候创建”、“什么时候销毁”这些问题。当权威端调用 Spawner 的 spawn 接口来创建一个场景实例，也就是游戏对象的时候，Spawner 会把这个创建请求以 <u>*可靠传输*</u> 的方式发送给其它所有客户端，促使他们在本地实例化一个完全相同的节点，并且保持节点名称、网络ID等关键信息相互对应。之后，Spawner 会持续跟踪这个实例，当权威端毁这个对象时，Spawner 会发送一个 despawn 通知，让其他客户端也删除对应的对象副本。需要注意的是，Spawner 默认只保证场景 <u>*结构的正确性*</u> 和对象实际的 <u>*存在性*</u>，对象身上的具体字段值，比如服务器上临时修改的某个变量，通常需要依靠 MultiplayerSychronizer 组件配置同步，或者额外编写 RPC 来同步。

_MultiplayerSpawner节点面板_
如图，在使用 MultiplayerSpawner 节点时，需要指定好要生成的是哪个场景资源，以及新生成的这个场景对象要放到场景树的哪个节点下面。
- **MultiplayerSychronizer**：专门负责状态同步的组件，它的职责是把某个节点上的那些被标记为需要同步的属性的值，按照设计好的策略发送给其他客户端。他管的是状态同步，比如字段的初始值是什么，运行中发生了哪些增量变化，以及根据可见性进行过滤同步等。但他不负责节点的创建和销毁，那是上面 MulitplayerSpawner 的工作。在 Godot 的编辑器里使用它，感觉上就有点像动画编辑器里面的配置轨道，都是需要去索引到当前场景里某个特定节点的某个特定字段上。
![MultiplayerSychronizer添加同步属性](assets/img/2026-04-17-Godot4.5是如何封装和实现高级网络功能的/image2.png)
_MultiplayerSychronizer添加同步属性_
一旦某个属性被添加到这个列表中，它就会被引擎纳入到网络同步的流程中。这里我们可以看到有两列重要的参数可以配置，出生和复制：
  - **出生**：指的是当权威端生成这个节点时，这个字段的当前值会随着生成命令，一并发送给其他客户端，作为这个对象副本的初始状态，相当于自动完成了初始化。
  - **复制**：指的是相应字段在运行中的同步策略，分为从不、始终、更改时 3 个选项：
    - **从不**：就是完全不同步这个字段。
    - **始终**：意味着它会以一个固定的时间间隔 tick 持续的发送最新的值。不管这个值变没变，字段的更新会以不可靠的传输模式持续发送。频繁变化的值，比如位置，是可以容忍丢失的。
	- **更改时**：就是基于脏标记的增长更新，只在字段的值真正发生变化时，才发送一次新的值。字段的更新会以可靠的传输模式在值变化的时候发送。偶尔变化的关键值，那必须要保证送达。
